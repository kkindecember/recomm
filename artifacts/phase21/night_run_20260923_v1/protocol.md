# 21.4C 重启前并行与断点恢复

## 执行依据与范围

- Origin Skill：academic-research-suite / experiment-agent，run模式；2026-09-23。
- 用户说明今晚服务器会重启，要求今天的实验尽力跑、重启后先停，并保证以后方便恢复。
- 本协议只调整调度、保存和恢复，覆盖21.3E两专家贡献/机制检查与21.4B文本A/B/C及条件D。两批科学设置、样本、拟合配方和升级门槛保持原冻结定义。
- 18:37左右GPU快照：0/2/3/4号卡各有约27–29GiB空闲；6/7号卡正在运行本批任务。原两进程限制是保守调度限制，不是其他GPU显存不足。

## 重启前安排

使用一个新监督器接管旧的两个调度器，避免争抢同一GPU。只停止旧调度进程本身，已启动的两个真实生成工作进程保持运行，并记录接管前状态、启动记录、PID、启动时刻和系统boot ID。

- 总并发上限6个GPU工作进程，同一GPU最多一个本批工作进程；保留原GPU池，不触碰别人的进程。
- 启动门槛仍为至少16GiB空闲显存，单进程PyTorch上限11GiB、CPU线程2；卡实际变忙则排队。
- 文本缓存筛查优先获得新增空槽，同时推进剩余专家机制组。两域数据和文件独立，本次允许同一组两域并行；不再因Toys未完成而阻塞Beauty。
- 真实单任务4小时上限，短期速度估计只提示。监督器每次运行48小时上限；退出不强行破坏其他已经在跑的任务。
- Text缓存升级到真实生成及D的条件完全照21.4B，不为了赶时间变更实验门槛。

## 保存与恢复边界

1. 已完成且核验通过的域级任务直接跳过；已完成的融合器和全目录分数核对后复用。
2. 新生成任务每完成一个用户即写入predictions.jsonl并fsync；已在跑的旧生成任务仍逐用户flush，新监督器约每分钟额外fsync现有预测文件。
3. 恢复时核对预测记录的用户顺序、目标、历史、样本索引、分数和原生候选一致性，从第一个未保存用户开始计算。全部512人齐备后再运行原完整结果核验。
4. 重启若留下半行JSON，仅备份并截去最后残缺行；完整行损坏、顺序错误或输入哈希变化会报错，不能静默跳过。
5. 已完成的训练结果复用；如果中断在融合器尚未完整保存的阶段，保留旧半成品，再重做该短小的4轮融合拟合。没有承诺逐优化步恢复。
6. 文本评分矩阵当前没有逐行提交标记。若缓存评分/拟合任务中断，保留对应attempt，再重做该域缓存任务；不会因此重跑其他完成的域或已保存的生成用户。
7. 配置、原始实验代码和旧manifest不改写。新增调度/恢复代码、协议与操作配置单独冻结，输出仍写各实验原目录，恢复行为写入continuation.json与独立attempt日志。
8. 系统重启后不自动重启任务，不安装开机服务。状态文件可能停留RUNNING，需检查系统boot ID与进程身份，不能只凭遗留PID判定仍运行。
9. 新监督器运行中出现程序错误不自动重试；保留错误与部分结果。手动resume会恢复被重启打断的任务；真实FAILED默认保留，诊断修复后才显式加--retry-failed。

## 入口

首次：`bash experiment/phase21/run_night.sh start`。

重启后手动恢复：`bash experiment/phase21/run_night.sh resume`。该命令会检查已有成果，只补未完成部分。若要离开终端继续跑，可在项目目录使用：

```bash
tmux new-session -d -s s21_night_20260923 'bash experiment/phase21/run_night.sh resume >> artifacts/phase21/night_run_20260923_console.log 2>&1'
```

当前统一状态：`artifacts/phase21/night_run_20260923_v1/status.json`；两批原status.json同步更新并标明managed_by。启动记录和接管记录也在该新目录。用户只需以后说明“恢复今晚的实验”，即可沿此入口检查后续跑。

结果解释：中断和资源停止不是负结果。任何部分生成指标不能冒充完整512人比较；最终仍以各域核验完成的报告为准。
